# 00. Звіт про аудит репозиторію (Repository Audit Report)

## 1. Executive Summary (Резюме для керівництва)

Цей звіт містить комплексний, детальний аудит репозиторію **kovichka-s/erp-migration-case**, який представляє собою портфоліо бізнес-аналітика (BA Portfolio Case) для проєкту міграції ERP-системи з платформи «1С» на Odoo ERP.

Аналіз виконано з чотирьох взаємодоповнюючих точок зору:
1. **Старшого бізнес-аналітика (Senior BA):** оцінка методологічної глибини, відповідності стандартам BABOK v3 та BPM CBOK, повноти аналізу поточного й цільового станів.
2. **Менеджера з найму (Hiring Manager):** оцінка репозиторію як професійного портфоліо кандидатури на позицію Senior BA/BSA.
3. **Стейкхолдера проєкту (Project Stakeholder / Sponsor):** перевірка зрозумілості бізнес-кейсу, простежуваності очікуваної цінності та обґрунтованості інвестицій.
4. **Команди розробки (Development Team):** оцінка придатності вимог, специфікацій та моделей процесів для безпосереднього проектування та розробки рішення на базі Odoo ERP.

**Ключовий висновок:** Репозиторій є надзвичайно якісним, глибоким та реалістичним прикладом бізнес-аналізу у сфері ERP-впровадження. Проєкт має логічний наскрізний ланцюжок: від виявлення бізнес-проблеми через аналіз поточного процесу (AS-IS, RCA, VSM) до побудови детальних вимог та цільового процесу (TO-BE, Gap Analysis). Разом із тим, аудит виявив кілька критичних зауважень, логічних суперечностей, прогалин у трасуванні та незавершених шаблонів-заглушок, усунення яких дозволить підвищити оцінку портфоліо до найвищого професійного рівня (Production-Ready).

## 3. Document-by-Document Review (Детальний аналіз кожного документа)

### Phase 1 & 2. Project Initiation & Discovery

#### **01. Project Charter (Статут проєкту)**
* **Мета та релевантність:** Дуже висока. Чітко позиціонує проєкт як заміну «1С» на Odoo через зміну законодавства України, що є надзвичайно актуальним кейсом для українського ринку.
* **Структура та мова:** Професійна, структурована термінологія. Ролі визначені за стандартом.
* **Прогалини / Зауваження:** Розділ "Expected Business Value" є суто якісним (наприклад, "швидше відповідати клієнтам"), у ньому бракує кількісних цілей (KPI), які згодом з'являються у файлі 21. Доцільно додати перехресне посилання на `docs/21_KPI_Definition.md`.

#### **02. Stakeholder Analysis (Аналіз зацікавлених сторін)**
* **Мета та релевантність:** Документ корисний для планування комунікацій та тестування (UAT).
* **Структура та мова:** Наявність розділів "Джерела бізнес-вимог", "Хто погоджує рішення" та "Хто братиме участь у тестуванні" додає практичної цінності.
* **Прогалини / Зауваження:** Стейкхолдери описані досить загально. Було б корисно оцінити їх за класичною матрицею Power/Interest (Влада/Інтерес) та вказати стратегію залучення для кожного (наприклад, "Keep Informed", "Manage Closely").

#### **03. Stakeholder Interviews (Інтерв'ю зі стейкхолдерами)**
* **Мета та релевантність:** Має демонструвати первинний збір вимог (Elicitation).
* **Прогалини / Зауваження (Критично для портфоліо):** Документ є **незавершеним шаблоном**. Розділи "Інтерв'ю №2", "Інтерв'ю №3" мають позначку `*Заплановано*`, а "Загальні спостереження" містять шаблонний текст `(Заповнюється після завершення всіх інтерв'ю.)`. Це створює негативне враження у Hiring Manager, оскільки виглядає як "кинута на півдорозі" робота. Необхідно заповнити інтерв'ю з Керівником складу пелет (SME) та Логістом, оскільки їхні болючі точки прямо впливають на подальші вимоги.

#### **04. Business Problem Statement (Формулювання бізнес-проблеми)**
* **Мета та релевантність:** Чудово пов'язує технічну міграцію із бізнес-ефектом. Чітко зазначає, що мета міграції — не просто "копіювання процесів 1С в Odoo", а реінжиніринг з метою усунення втрат.
* **Структура та мова:** Повна, логічна, з правильним фокусом на наслідки для клієнтів та компанії.

#### **05. Scope Definition (Опис меж проєкту)**
* **Мета та релевантність:** Класичний документ управління рамками проєкту.
* **Прогалини / Зауваження:** У розділі "Assumptions" зазначено: "мінімальний обсяг продажу становить 10 Big Bag". Це припущення насправді є жорстким бізнес-правилом (BR-004). Краще перенести його до реєстру бізнес-правил або зробити посилання на нього.

### Phase 3. Current State Analysis (AS IS)

#### **06. AS IS Process Description (Опис поточного процесу)**
* **Мета та релевантність:** Покроковий опис кроків 1–8. Дає чітку картину ручного хаосу та відсутності прозорості.
* **Прогалини / Зауваження:** У кроці 1 зазначено, що кількість відходів залежить від виробничого плану основної продукції, але не розкрито, де саме цей план ведеться у поточному стані (в "1С" чи в Excel). Це ускладнює розуміння "Data Gap" для команди розробки.

#### **07. BPMN AS IS (Опис та діаграма)**
* **Мета та релевантність:** `07_BPMN_AS_IS.md` виступає текстовою обгорткою для файлу `diagrams/BPMN_AS_IS_End_to_End.pdf`.
* **Якість діаграми:** Діаграма в PDF виконана професійно у нотації BPMN 2.0. Вона показує наскрізний процес. Проте, вона занадто широка для швидкого аналізу стейкхолдерами. Було б чудово додати її декомпозицію безпосередньо у markdown за допомогою вбудованого рендерингу Mermaid або хоча б зображень PNG.

#### **08. Value Stream Mapping (VSM) (Карта потоку створення цінності)**
* **Мета та релевантність:** Рідкісний та надзвичайно сильний артефакт для портфоліо бізнес-аналітика. Показує зрілість BA у практиках Lean/Six Sigma.
* **Структура та якість:** Прекрасно розписано матеріальні та інформаційні потоки, а також додану/недодану вартість (Value Added / Waste Analysis).
* **Прогалини / Зауваження:** У розділі "Process Metrics" перелічено метрики (Lead Time, Waiting Time), але немає їхніх фактичних поточних значень (наприклад, "Lead Time = 5 днів, з яких 3 дні — очікування"). Без цифр VSM залишається суто теоретичним описом.

#### **09. Pain Points Analysis (Аналіз болючих точок)**
* **Мета та якість:** Чітко виділено 7 больових точок з оцінкою Severity (High/Medium). Кожна точка має логічний зв'язок із бізнес-проблемою та процесом.
* **Зв'язок:** Повністю узгоджується із документами Discovery.

#### **10. Root Cause Analysis (Аналіз першопричин)**
* **Мета та якість:** Використання методу "5 Whys" проведено бездоганно. Встановлено логічний ланцюжок від відсутності відповіді клієнту до відсутності інтегрованої End-to-End моделі в ERP.
* ** suitability для BA портфоліо:** Відмінна демонстрація аналітичного мислення (Problem Solving).

#### **11. Business Rules (Бізнес-правила)**
* **Мета та якість:** Визначено 11 бізнес-правил. Правила розділені за напрямами (виробництво, логістика, продажі).
* **Прогалини / Зауваження:** Деякі правила сформульовані розмито. Наприклад, **BR-001** та **BR-002** кажуть про залежність від типу продукції, але не дають конкретних коефіцієнтів утворення відходів (наприклад: "1 куб.м меблевого щита створює 0.15 тон тирси, а 1 куб.м дошки — 0.05 тон"). Для команди розробників Odoo ці правила мають бути алгоритмічними, інакше їх неможливо закодувати.

### Phase 4. Requirements Analysis

#### **12. Functional Requirements (Функціональні вимоги)**
* **Мета та якість:** Наведено 12 вимог (FR-001 — FR-012). Кожна вимога містить опис, зацікавлених користувачів та критерії.
* **Прогалини / Зауваження (Суперечність з Decision Log):**
  * **FR-02** вимагає від системи показувати "прогнозований строк готовності". Проте в `24_Decision_Log.md` під кодом **PD-01** це рішення ("автоматичне прогнозування дати готовності") позначено як **Відкладене (Postponed)**. Це груба логічна суперечність. Якщо рішення відкладене, вимога FR-02 не може бути реалізована в межах першої черги, або вона повинна мати інший, спрощений (ручний) механізм, який не описано.
  * Вимоги сформульовані у пасивному стані ("Система повинна відображати"), що є прийнятним, але деякі критерії є занадто загальними ("Система повинна забезпечити єдине джерело інформації").

#### **13. Non-functional Requirements (Нефункціональні вимоги)**
* **Мета та якість:** Наведено 12 детальних нефункціональних вимог, що охоплюють безпеку, продуктивність, масштабованість, якість даних та міграцію.
* **Прогалини / Зауваження:** Вимоги сформовані якісно, але деякі з них не мають вимірюваних KPI (наприклад, NFR-001 "без значних затримок" замість "час завантаження сторінки до 2 секунд"). Також більшість із них (з NFR-06 по NFR-12) повністю загублені в матриці RTM.

#### **14. User Stories (Користувацькі історії)**
* **Мета та якість:** Сформовано 7 історій (US-01 — US-07). Вони покривають ключові ролі: менеджер з продажу, керівник складу, керівник виробництва, власник компанії.
* **Прогалини / Зауваження:** Критерії прийняття (Acceptance Criteria) всередині User Stories написані у форматі списку, який просто дублює функціональні вимоги. Вони не використовують професійний формат тестування (Gherkin `Given-When-Then`), що знижує цінність документа для QA-інженерів.

#### **15. Use Cases (Сценарії використання)**
* **Мета та якість:** Наведено 7 сценаріїв (UC-01 — UC-07). Документ структурований, містить акторів, передумови, основні та альтернативні сценарії.
* **Прогалини / Зауваження:**
  * У жодному Use Case немає розділів **"Винятки" (Exceptions)** та **"Післяумови" (Postconditions)**, що є обов'язковим елементом класичного системного аналізу за Коберном.
  * Наприклад, у UC-04 (Планування відвантаження) не описано сценарій, коли перевізник відмовляється від замовлення або коли вартість доставки перевищує допустиму маржу.

#### **16. Acceptance Criteria (Критерії прийняття)**
* **Мета та якість:** 8 комплексних критеріїв прийняття, прив'язаних до US та UC.

## 4. Critical Issues (Критичні зауваження та дефекти)

Під час аудиту було виявлено 5 критичних проблем, які безпосередньо впливають на якість репозиторію як портфоліо та його корисність для розробки:

1. **Відсутність цільової схеми TO-BE (Missing Artifact):**
   * *Опис:* Файл `diagrams/19_BPMN_TO_BE.pdf` відсутній у репозиторії. Неможливо візуально оцінити цільовий процес.
   * *Вплив:* **Критичний.** Hiring Manager не бачить навичок проектування цільового стану. Розробники не мають графічної карти для налаштування Odoo.

2. **Логічна суперечність між вимогами та журналом рішень (Logical Inconsistency):**
   * *Опис:* Рішення про автоматичне прогнозування готовності продукції (**PD-01**) відкладено (Postponed). Проте вимоги **FR-02** та бізнес-правило **BR-010** вимагають реалізації цього прогнозу в поточному обсязі (Scope).
   * *Вплив:* **Високий.** Створює суперечливі вказівки для команди розробки. Незрозуміло, чи потрібно розробляти алгоритм прогнозування в першій черзі.

3. **Незавершені шаблони в інтерв'ю (Incomplete Artifacts):**
   * *Опис:* `03_Stakeholder_Interviews.md` містить лише одне інтерв'ю. Секції для інших інтерв'ю та загальні висновки залишені як заглушки (`*Заплановано*`).
   * *Вплив:* **Середній.** Псує професійне враження про портфоліо, демонструючи незавершеність роботи.

4. **Прогалини в матриці трасування NFR (Requirements Gap):**
   * *Опис:* Нефункціональні вимоги **NFR-06 — NFR-12** повністю пропущені в матриці трасування RTM (`17_Requirements_Traceability_Matrix.md`).
   * *Вплив:* **Середній.** Ризик того, що критичні вимоги (такі як міграція даних, аналітика, гнучкість) будуть пропущені під час розробки та тестування.

5. **Шаблонні дати в журналі рішень (Formatting Issue):**
   * *Опис:* Використання дат `DD-MM-YYYY` у `24_Decision_Log.md` замість реальних календарних маркерів.
   * *Вплив:* **Низький.** Створює відчуття незавершеності або "швидкого копіювання" шаблону.

## 6. Missing Artifact Recommendations (Рекомендації щодо нових артефактів)

Для значного підвищення професійного рівня портфоліо та полегшення роботи команди розробки Odoo, рекомендується додати такі документи:

### 1. Словник термінів (Glossary)
* **Чому це важливо:** Впровадження ERP вимагає спільної мови між бізнесом (лісники, складські працівники, логісти) та розробниками Odoo. Терміни на кшталт "Big Bag", "Меблевий щит", "Деревні відходи", "Товщина пропилу", "Коефіцієнт ущільнення" мають бути чітко стандартизовані.
* **Яке питання вирішує:** Усуває неоднозначність у трактуванні бізнес-понять розробниками та тестувальниками.
* **На чому базується:** На основі AS-IS Process (06) та Business Rules (11).
* **Місце в репозиторії:** `docs/26_Glossary.md` (Рекомендовано).

### 2. Матриця ролей та повноважень Odoo (Role and Permission Matrix)
* **Чому це важливо:** Odoo використовує жорстку рольову модель доступу (Access Control Lists / Record Rules). Необхідно детально розписати, які права (Створення, Читання, Оновлення, Видалення - CRUD) мають різні ролі на бізнес-об'єкти Odoo (Картка Клієнта, Замовлення на продаж, Складська переміщення, Виробниче замовлення).
* **Яке питання вирішує:** Які користувачі мають доступ до конфіденційної інформації та хто має право погоджувати відвантаження.
* **На чому базується:** Stakeholder Analysis (02) та Use Cases (15).
* **Місце в репозиторії:** `docs/27_Role_and_Permission_Matrix.md` (Необхідно / Essential).

### 3. Стратегія міграції даних та Специфікація мапінгу (Data Migration Strategy)
* **Чому це важливо:** Оскільки це міграція з «1С» на Odoo, найскладнішою технічною частиною є перенесення історичних даних (довідники клієнтів, номенклатура продукції, початкові складські залишки).
* **Яке питання вирішує:** Як саме дані будуть очищені, трансформовані та завантажені в Odoo (ETL-процес). Які поля «1С» відповідають полям в Odoo.
* **На чому базується:** Gap Analysis (20 - Data Gap) та Non-functional Requirements (NFR-011).
* **Місце в репозиторії:** `docs/28_Data_Migration_Strategy.md` (Необхідно / Essential).

### 4. Беклог продукту та Пріоритезація вимог (Product Backlog & Prioritization)
* **Чому це важливо:** Демонструє володіння Agile/Scrum методологіями. Перетворює 12 функціональних вимог на беклог історій з MoSCoW-пріоритезацією (Must Have, Should Have, Could Have, Won't Have) або WSJF (Weighted Shortest Job First).
* **Яке питання вирішує:** З чого команда розробки повинна почати реалізацію та що ввійде до MVP (Minimum Viable Product).
* **На чому базується:** Functional Requirements (12) та User Stories (14).
* **Місце в репозиторії:** `docs/29_Product_Backlog.md` (Рекомендовано).

### 5. План тестування користувачами та Тестові сценарії (UAT Plan & Test Scenarios)
* **Чому це важливо:** Забезпечує перевірку готовності системи перед запуском (Go-Live).
* **Яке питання вирішує:** Як саме бізнес-користувачі (менеджер з продажу, логіст, бухгалтер) перевірять, що Odoo працює відповідно до вимог.
* **На чому базується:** Acceptance Criteria (16) та Use Cases (15).
* **Місце в репозиторії:** `docs/30_UAT_Plan.md` (Рекомендовано).
