# Definition of Done (DoD)

## Мета

Definition of Done визначає критерії, за якими User Story, Requirement або інша задача вважається повністю виконаною та готовою до прийняття бізнесом.

DoD забезпечує єдине розуміння команди щодо того, що означає "Done", і допомагає уникнути ситуацій, коли задача формально завершена, але результат ще не готовий до використання.

---

## Критерії готовності

### 1. Реалізація

- Функціональність реалізована відповідно до Functional Requirements.
- Реалізовані всі погоджені сценарії.
- Враховані визначені Edge Cases.
- Реалізація відповідає погодженому Scope.

### 2. Acceptance Criteria

- Усі Acceptance Criteria виконані.
- Результат перевірений відповідно до визначених критеріїв.
- Виявлені невідповідності виправлені або окремо зафіксовані.

### 3. Business Rules

- Усі релевантні Business Rules враховані.
- Реалізація не суперечить погодженим правилам процесу.

### 4. Testing

- Виконано необхідне функціональне тестування.
- Критичні сценарії перевірені.
- Виявлені критичні дефекти виправлені.
- Результати тестування зафіксовані.

### 5. Business Acceptance / UAT

- Проведено UAT, якщо він передбачений процесом.
- Ключовий бізнес-користувач або відповідальний Stakeholder підтвердив відповідність результату бізнес-потребі.
- Результат відповідає погодженим Acceptance Criteria.

### 6. Documentation

За необхідності оновлено:

- Functional Requirements;
- User Stories;
- Use Cases;
- Acceptance Criteria;
- Business Rules;
- BPMN / Process Documentation;
- Requirements Traceability Matrix;
- User Documentation.

Документація відповідає фактично реалізованій функціональності.

### 7. Traceability

- Задача пов'язана з відповідною User Story.
- User Story пов'язана з відповідним Epic.
- Acceptance Criteria перевірені.
- Зміни мають необхідні посилання в Requirements Traceability Matrix.

### 8. Non-functional Requirements

Якщо вони застосовуються:

- перевірені визначені Non-functional Requirements;
- виконані погоджені вимоги щодо продуктивності;
- безпеки;
- доступності;
- надійності;
- сумісності.

### 9. Release Readiness

- Відсутні критичні дефекти, що блокують використання функціональності.
- Визначені всі відомі обмеження.
- Необхідні залежності виконані.
- Функціональність готова до Release або передачі бізнесу.

---

## Definition of Done Checklist

- [ ] Функціональність реалізована
- [ ] Scope дотримано
- [ ] Functional Requirements виконані
- [ ] Business Rules враховані
- [ ] Acceptance Criteria виконані
- [ ] Edge Cases перевірені
- [ ] Необхідне тестування виконано
- [ ] Критичні дефекти усунені
- [ ] UAT проведено, якщо необхідно
- [ ] Business Stakeholder прийняв результат
- [ ] Документація актуалізована
- [ ] Requirements Traceability оновлена
- [ ] Non-functional Requirements перевірені, якщо застосовуються
- [ ] Відомі обмеження зафіксовані
- [ ] Задача готова до Release

## Definition of Done Decision

### DONE

Задача може бути переведена у статус **Done**, якщо всі критичні критерії виконані та результат прийнятий відповідальною стороною.

### NOT DONE

Задача не може бути визнана завершеною, якщо:

- не виконані Acceptance Criteria;
- залишилися критичні дефекти;
- не проведено необхідне тестування;
- результат не відповідає погодженим вимогам;
- відсутнє необхідне Business Acceptance;
- документація не відповідає фактичній реалізації.

## Відповідальність

**Development Team**

- реалізація функціональності;
- виправлення дефектів;
- технічне тестування;
- забезпечення відповідності реалізації вимогам.

**Business Analyst**

- перевірка відповідності реалізації вимогам;
- перевірка Acceptance Criteria;
- підтримка актуальності документації;
- координація Business Acceptance.

**Business Stakeholder / Product Owner**

- підтвердження відповідності бізнес-потребі;
- прийняття результату.

**QA**

- перевірка функціональності;
- виконання тестових сценаріїв;
- фіксація та перевірка дефектів.
